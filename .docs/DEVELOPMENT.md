# Risovach DEVELOPMENT.md

Постоянный контракт проекта и зафиксированное направление. Прочитай `AGENT_PROMPT.md` как главный промпт сессии.

## Источник истины

При конфликтах используй этот порядок:

1. последнее явное решение пользователя;
2. зафиксированные правила в этом файле;
3. принятые решения в `.docs/DECISIONS.md`;
4. дизайн-документы и README модулей;
5. существующий код и допущения.

Если конфликт важен - остановись и скажи пользователю. Не выбирай молча долгосрочную архитектуру.

## Проект

- Бэкенд: `backend/` - Bun + Elysia + Drizzle ORM + SQLite. Прод-файл `data/db.sqlite` живёт локально на этой машине.
- Фронтенд: `frontend/` - React 19, Vite, TanStack Router/Query, Zustand, Konva (канвас-редактор).
- Workspace: корневого workspace нет; `backend/` и `frontend/` - самостоятельные проекты со своими `package.json` и lock-файлами. Корень содержит только `.docs/`, `.zed/`, `AGENTS.md`, `backend/`, `frontend/` и служебные git-файлы.
- Логгер: npm-пакет `hp_logger` (github.com/HullPerse/hp_logger) - логгер с транспортами, redaction и метриками Prometheus; backend зависит от него как от обычной npm-зависимости (`^0.1.1`).
- Схема БД (`backend/src/db/schema.db.ts`) - единственный источник истины для структуры БД. Миграционные файлы и таблица `__drizzle_migrations` не используются.
- Документация проекта - в `.docs/`. Она живет только локально и не трекается в Git (покрыта `.gitignore`).
- `.docs/DECISIONS.md` - обязательный журнал существенных решений и изменений поведения, а не только ответов на вопросы.

## Зафиксированные решения

- Пакетный менеджер: Bun. Все команды в документации пишутся на Bun.
- Lint/format: ultracite + oxlint/oxfmt. Скрипты `check`/`fix` через ultracite, `lint` через oxlint.
- Язык проекта: русский. Ответы агента, документация и UI-копии на русском.
- Миграции применяются вручную через drizzle-kit push: `bun run db:migrate` (NODE_ENV-зависимо). Тесты сами применяют схему к test-БД.
- Админ выдаётся по id через интерактивный `bun run db:seed`: команда спрашивает ID пользователя и ставит ему `role=admin` (повторные запуски безопасны).
- Роли пользователя: `user` (по умолчанию), `admin`, `subscriber` (зарезервирована).
- Модель потока данных: серверные данные фронтенд получает через TanStack Query и API-клиенты. Query обязан явно использовать `isLoading`/`isError`, фоновое обновление учитывается отдельно через `isFetching`.
- В файле предпочтителен максимум один `useQuery`/`useSuspenseQuery`. Один query может возвращать составной типизированный DTO для связанных данных, например `data?.lobby.count` и `data?.profile.username`. Несколько запросов допустимы для действительно независимых данных, но причину нужно назвать и не создавать искусственную последовательность запросов только ради правила.
- Результат query обычно оставляется в переменной `data` без переименования. Компонент использует фактическую форму ответа, например `data?.count`, `data?.value` или `data?.object1.value`; универсальное поле `value` не добавляется только ради одинакового доступа. Независимые ресурсы не объединяются только ради уменьшения числа query.
- Явный `any` запрещён в написанном коде. `unknown` разрешён только внутри boundary-кода для JSON, `catch`, внешних библиотек и transport adapters; перед выходом в доменную или UI-логику он должен быть сужен через Zod или type guard.
- Общие типы и интерфейсы хранятся в `types/*.d.ts` (проектная конвенция: `.d.ts` используется и для общих типов, не только для ambient-объявлений). Общие helpers и микрофункции - в `lib/*.utils.ts`, статические конфиги и hardcoded data - в `config/*.config.ts`, хуки - в `hooks/**/*.hook.ts`, API-клиенты и классы связи с сервером - в `api/**/*.api.ts`. Локальные исключения допустимы только после согласования конкретного пути с пользователем.
- Basename файлов компонентов пишется в camelCase без дефисов; служебные суффиксы `.component.tsx`, `.canvas.tsx` и другие сохраняются.
- Отказано (внедрять не нужно): слой репозиториев интерфейс+model+impl, overlay-либы, sandbox-исполнение JS, NATS-шина (пока монолит).
- Обозначение `(recommended)` при вариантах - обязательно для рекомендаций агента; добавляется только когда есть реальное обоснование. В multi-select marker может стоять на отдельных опциях, но не означает выбрать все marked options.
- Для каждой новой фичи отдельно фиксируются implementation disposition и documentation destination.
- Вопросов может быть сколько угодно, но только содержательных: без вопросов, на которые отвечает код или документация, и без мусорных уточнений.
- Для новой зависимости агент сначала проверяет установленные пакеты и их фактическое использование. Если подходящего пакета нет, агент предлагает несколько современных вариантов и рекомендуемый вариант с кратким сравнением поддержки, лицензии, размера и производительности. Новая зависимость не добавляется молча.

## Типизация по языкам

Базовые правила типизации фиксируются при инициализации под язык проекта. Проект написан на TypeScript:

- **TypeScript**: явный `any` запрещён в написанном коде; `unknown` только в boundary-коде (разбор JSON, `catch`, внешние библиотеки, transport adapters) и сужается через Zod или type guard до входа в доменную/UI-логику; `strict: true`.

Для другого языка агент формулирует эквивалент в том же духе и согласует его с пользователем.

## Сравнение пакетов с бенчмарком

Когда сравниваются 2+ конкурирующих пакета в одной категории, до рекомендации напиши и запусти минимальный микробенчмарк. Не опирайся только на заявления документации или внешние бенчмарки, которые могут быть устаревшими.

**Когда бенчмарк нужен:** пакеты, напрямую влияющие на горячие пути (HTTP-фреймворки, парсеры, сериализация, построители запросов ORM, бандлеры, тест-раннеры). Агент решает по тому, является ли производительность значимым различием для категории.

**Когда можно пропустить:** утилитарные библиотеки, где производительность не главное (lodash против ramda, форматтеры дат, конвертеры цветов).

**Правила бенчмарка:**

1. Напиши маленький скрипт, который выполняет именно нужную проекту операцию, а не общий hello-world.
2. Запусти его на рантайме проекта (Bun) и приведи реальные числа.
3. Приложи скрипт бенчмарка к таблице сравнения рядом с заявлениями документации.
4. Если числа близки (в пределах 10%), помечай как "equivalent" и рекомендуй по другим критериям (API, размер бандла, поддержка).
5. Если числа расходятся значительно, отметь разрыв и взвесь его против эргономики, размера бандла и экосистемы.

### Чеклист производительности (когда есть бюджет или подозрение)

- Цели Core Web Vitals определены до оптимизации: LCP, INP, CLS с порогами;
- сначала измерь, потом оптимизируй: профилирование, бенчмарк или трейс; без измерения нет утверждения;
- проверяй размер бандла и стоимость импорта для каждой новой зависимости;
- проверяй горячие пути на аллокации, IO, кэши и канселяцию.

### Чеклист наблюдаемости (когда проект работает в продакшене)

- структурное логирование: уровень, сообщение, объект контекста; без секретов и PII в логах;
- метрики: RED (rate, errors, duration) или USE (utilization, saturation, errors) с названными порогами;
- трейсинг: спаны границ для внешних вызовов, где это уместно;
- алерты по симптомам, а не по шуму; у каждого алерта есть владелец и указатель на runbook.

Оба списка - дополнения, а не замена правилу бенчмарка.

## Протокол коммуникации агента

Агент должен:

1. читать релевантные доки и код до предложения реализации;
2. сообщать, что нашёл и что предполагает;
3. уточнять неполное понимание до реализации: пересказывать интерпретацию одним предложением, когда неясны цель, границы или ожидаемый результат;
4. спрашивать перед неоднозначным архитектурным, UX, безопасностным, лицензионным или публично-API решением;
5. давать минимум два варианта и последствия для важных решений;
6. до кода спрашивать implementation disposition новой фичи (сейчас, deferred или rejected) и documentation destination (существующий feature-файл, новый feature-файл или только DECISIONS.md);
7. использовать план и чеклист для многошаговой работы;
8. отчитываться после каждого выполненного шага, а не только в конце;
9. явно называть противоречия, отсутствующие требования, возможности оптимизации и UX-риски;
10. предпочитать минимальное связное изменение спекулятивной архитектуре;
11. обновлять `.docs/DECISIONS.md` при каждом существенном решении, изменении поведения или исправлении пользовательского бага, а README - когда работа меняет команды, структуру или конвенции;
12. проверять нетривиальный код typecheck-ом, lint и релевантными тестами;
13. добавлять тесты каждой новой фиче до отметки `done`;
14. честно сообщать о неудачных проверках и о том, что осталось непроверенным;
15. останавливаться, а не угадывать, когда выбор может увести проект в дорогой путь;
16. следовать протоколу вопросов из `AGENT_PROMPT.md` (батчинг, делегирование, отложенные, конфликты, запись решений);
17. рекомендовать `.docs/REVIEWER.md` для независимого ревью крупных изменений.

Агент не должен:

- молча переопределять продукт;
- добавлять библиотеку без проверки текущего стека, лицензии и необходимости;
- запускать деструктивные или необратимые команды без явного разрешения;
- ставить инструменты без разрешения, если установка не требуется для запрошенной проверки;
- заявлять, что фича завершена, когда есть только заглушка или визуальный макет;
- отмечать фичу завершённой без её тестов или явно одобренного исключения;
- прятать трейдоффы за расплывчатыми формулировками;
- делать несвязанные рефакторы при реализации фичи;
- использовать `any` или протаскивать `unknown` из boundary-кода в доменную/UI-логику;
- молча оставлять локальные типы или helpers вне закреплённых каталогов;
- добавлять упоминания ИИ-агента, co-author trailers или любой другой текст про ИИ-агента в сообщения коммитов, аннотации push или описания PR на GitHub.

## Прямой критический режим

- Агент не поддакивает плохой идее. Если запрос ненужен, вреден, преждевременен, чрезмерно сложен, противоречит scope или создает неоправданный риск, агент сначала дает прямой verdict.
- Разбор обязан назвать конкретную проблему, последствия, альтернативу и условие, при котором verdict может измениться.
- Можно использовать резкий разговорный язык и ругань про идею или решение по запросу пользователя. Нельзя унижать пользователя как человека или подменять доказательный анализ оскорблением личности.
- Если предложение хорошее, агент так и говорит, не выдумывая критику.
- Если предложение плохое, агент обязан возразить и выбрать предпочтительный путь, а не прятаться за равноправным списком вариантов.
- Вопросы и варианты пишутся простым русским языком: короткий label, одно конкретное описание, без маркетинговых фраз, случайного английского и псевдотехнического жаргона.

## Disposition и destination новых фич

- Новая фича не переходит к реализации, пока пользователь не выбрал implementation disposition: реализовать сейчас, отложить с условием возврата или отклонить.
- Для каждой новой фичи пользователь отдельно выбирает documentation destination: существующий релевантный `.docs/features/*.md`, новый `.docs/features/<slug>.md` или только `.docs/DECISIONS.md`.
- Реализация и documentation destination не взаимоисключающие: фичу можно реализовать сейчас и одновременно записать в feature-файл.
- Для deferred/rejected решений обязательны причина, разрешенный scope и условие пересмотра либо явная запись, что пересмотр не планируется.
- Уже принятый disposition не спрашивается повторно, пока scope не изменился. Явная команда пользователя реализовать новую фичу считается disposition `сейчас`, но destination проверяется отдельно, если он не записан.
- В multi-select `(recommended)` добавляется только к отдельной опции с реальным обоснованием. Если options просто перечисляют равноценный набор возможностей, marker не нужен.
- Не использовать в options фразы вроде `better experience`, `seamless`, `scope-poop-based` и другие слова, которые не объясняют конкретное поведение или последствие.

## Формат feature-файлов

`.docs/features/*.md` - это рабочие документы решений, а не презентации и не большие технические спецификации. Пиши их почти как обычный текст: короткие заголовки для категорий, простые абзацы и короткие списки.

Для каждой идеи обязательно указывай:

- Идея: что предлагаем.
- Комментарий: зачем это нужно и какой у идеи статус.
- Плюсы: конкретная польза.
- Минусы: конкретные проблемы, цена или риск.

Если основной вариант спорный или слабый, добавляй альтернативы и сравнивай их.

Не используй тяжелое форматирование, декоративные таблицы и сложную вложенность без пользы. Пример старого и нового кода добавляй только при реальном изменении кода или поведения и показывай его в обычных fenced code blocks. Для planning-only идеи не выдумывай код.

Не переписывай старые feature-файлы целиком только ради нового стиля. Упрощай раздел, когда работаешь с ним по существу.

## Обязательный журнал решений

- Агент читает `.docs/DECISIONS.md` до аудита и учитывает его как источник истины.
- Любое существенное продуктовое, UX, архитектурное, техническое, безопасностное или персистентное решение, а также исправление пользовательского поведения записывается в `.docs/DECISIONS.md` в той же задаче.
- Запись добавляется до финального отчёта. Если задача не содержит существенных решений или изменений поведения, это явно указывается в отчёте.
- При конфликте с существующей записью агент останавливается и спрашивает пользователя, а не выбирает молча.
- В проекте могут параллельно работать несколько агентов. Журнал, остальные доки `.docs/` и текущий код - среда координации; выполняй четыре точки синхронизации из `AGENT_PROMPT.md` («Параллельные сессии») и не разрешай коллизии молча.

## Базовая безопасность

Контракт безопасности живёт в `.docs/SECURITY.md`: профиль, trust boundaries, capability budget, оси аудита и записанные команды. Базовые правила применяются к каждой задаче:

1. Сообщай о проблемах безопасности, когда их нашёл, в том числе вне scope текущей задачи; необъявленные каналы наружу и открытые живые секреты - это Blocker.
2. Каждый новый способ уйти наружу (сетевой вызов, дочерний процесс, запись в ФС, чтение окружения, lifecycle script) объявляется в capability budget в SECURITY.md с записью в DECISIONS.md до merge.
3. Секреты никогда не попадают в исходники, логи, фикстуры или доки; при подозрении на утечку креденшела сначала ротация, потом чистка истории.
4. Внешний ввод валидируется на trust boundary, через который он входит; внутреннее представление типизировано по разделу "Типизация по языкам".
5. Зависимости меняются только записанными командами из SECURITY.md: аудит до добавления, аудит после обновления; lock-файлы коммитятся.
6. Публикуемые пакеты доказывают отсутствие необъявленных каналов наружу по SECURITY.md до релиза.

Исправления безопасности подчиняются тем же правилам доказательств, что и тесты: точная локация, точный вывод команды, регрессионное покрытие там, где технически возможно.

## Anti-slop правила

Применяются к коду, документации, UI-копиям, ответам агента, сообщениям коммитов.

### Текст и пунктуация

- Не используй em/en dash (U+2014, U+2013). Только ASCII-пунктуация (дефис, запятые, двоеточие, скобки).
- Без длинных шаблонных вступлений, фейкового энтузиазма и повторных заключений.
- Без расплывчатых фраз вроде «бесшовный опыт», «надёжное решение» без измеримого смысла.
- UI-подписи короткие, прямые, действие-ориентированные.
- Сообщения об ошибках: что произошло и что делать дальше.

### Код и архитектура

- Комментарии редкие. Только для неочевидной причины, инварианта, обхода или ограничения безопасности.
- Без комментариев, пересказывающих код, и без гигантских doc-комментариев.
- Без спекулятивных абстракций, пустых точек расширения, неиспользуемых интерфейсов и фейковых плагинных систем.
- Без дублирующего стейта и дублирующих источников истины.
- Без повторной реализации уже существующей логики: до написания нового кода ищи по кодовой базе по смыслу (синонимы, родственные термины, похожие формы), а не только по имени; переиспользуй похожую реализацию или запиши в DECISIONS.md, почему новая обоснована.
- Явные имена, малые модули, типизированные ошибки, протестированная доменная логика.
- Без debug-логов, мёртвого кода, placeholder-путей успеха и фейковых данных в проде.
- Ошибки lint и typecheck исправляются или аргументируются; подавление без записанной причины не решение.
- Без TODO-комментариев вместо решения; записывай нерешённое в `.docs/DECISIONS.md`.
- Без голого `catch {}`. Каждый catch либо (1) использует Result-хелперы, когда сбой это нормальный поток, либо (2) сообщает через `console.error`/`warn`, либо (3) пишет наблюдаемое состояние (счётчик, маркер фолбэка), либо (4) несёт комментарий с охраняемым инвариантом и причиной, почему молчание безопасно.
- Предпочитай lookup-мапы цепочкам switch/if-else там, где набор значений стабилен и мапа строится один раз; switch оставляй только на действительно горячих ветках с разницей бенчмарка, которая его оправдывает.
- Не строй большую абстракцию под один гипотетический будущий случай.

### UI и UX

- Не добавляй UI лишь потому, что есть у другого продукта.
- Каждый контрол: пользовательская задача, ясное состояние, полезное состояние отказа.
- Предпочитай видимые контекстные действия скрытому глобальному поиску.
- Проектируй loading, empty, error, disabled, dirty, stale, recovery состояния до объявления поверхности готовой.
- Следуй `.docs/DESIGN.md` (нео-брутализм: radius 0, жёсткие границы 2px, хард-тени, моноширинный шрифт).

### Деслоп прозы: каталог шаблонов

Применяется к документации, feature-файлам, README, ответам агента, сообщениям коммитов и UI-копиям. Цель: убрать шаблоны, по которым читатель распознаёт машинный текст, не убив голос автора.

Проверки классифицируются перед применением: hard gate (недопустимо никогда), purpose gate (допустимо только с записанной причиной), quality lock (согласованность по всему тексту). Используй режим During (применяй во время письма) или After (аудит готового текста с нумерованными находками и одобрением до правок) и закрывай отчётом Delivery Gate. У комментариев к коду свой режим аудита: убирай декорацию, пересказ, нарратив и размытые TODO; оставляй комментарии с причинами, инвариантами, безопасностью и обходами. Provenance обязателен: никаких выдуманных чисел, цитат, отзывов, имён, заявлений о безопасности и производительности; гипотезы помечаются. Полная процедура - в скилле `deslop`.

Слова-теги (EN): delve, tapestry, realm, landscape (в переносном смысле), underscore (в переносном смысле), leverage, seamless, robust, crucial, pivotal, testament, foster, elevate, unlock, navigate (в переносном смысле), comprehensive, state-of-the-art, vibrant, rich (в переносном смысле), groundbreaking, renowned, breathtaking, stunning, world-class, boasts.

Слова-теги (RU): «бесшовный», «надёжное решение» без измеримого смысла, «стоит отметить», «не секрет, что», «в современном мире», «играет важную/ключевую роль», «открывает новые возможности», «инновационный» без факта, «уникальный» без факта, канцелярит («осуществлять проверку» вместо «проверять»).

Структурные шаблоны:

- раздувание значимости: произвольный факт подан как часть великого тренда («знаменует важный этап»);
- name-dropping авторитета: списки авторитетов без контекста;
- причастные хвосты: «...подчёркивая важность», «...отражая дух эпохи» в конце предложения;
- правило трёх: списки, искусственно добитые до трёх пунктов;
- отрицательный параллелизм: «не X, а Y» как трафарет абзаца; один раз это риторика, пять раз - шаблон;
- драматичная фрагментация: «Скорость. Вот и весь компромисс.»;
- риторическая подводка: «Результат? Ошеломляющий.»;
- прочистка горла: «Стоит отметить...», «Важно понимать...» - анонс мысли вместо самой мысли;
- демонстративный кикер: пустой оценочный обрывок после предложения;
- флажок важности: «Скорость здесь не сноска» вместо показа последствия;
- качели хеджирования: позиция не названа, контраргументы уравновешены; выбери сторону;
- размытая атрибуция: «эксперты считают» без названного источника;
- закрывающая сводка раздела: последний абзац пересказывает тот же абзац;
- фрактальная сводка: анонс -> сказанное -> пересказ сказанного;
- ложное действующее лицо: неодушевлённые вещи делают человеческие глаголы («компилятор хочет», «баг решает»);
- шаблонные секции «вызовы», кончающиеся восхвалением;
- надувающие наречия: genuinely, truly, actually, действительно, буквально, на самом деле;
- цитаты ради цитируемости, а не смысла.

Пунктуация и точность:

- em/en dash запрещены (см. выше); многоточие только как настоящее затухание речи;
- восклицательные знаки: максимум один на 1000 слов;
- двоеточие, обещающее развязку, обязано развязку дать;
- никогда не выдумывай числа, цитаты, источники, анекдоты; помечай гипотезы («представим», «imagine»);
- конкретика вместо общих слов: имя, число, место, время;
- активный залог с названным субъектом.

Сохранение голоса:

- отличай slop (бессмысленная формула) от голоса (осознанный выбор автора): короткий рубленый фрагмент после длинного предложения, несущий контраст, сильная закрывающая строка - это голос, не трогай;
- правки остаются точечными: меняй формулировку, не структуру аргумента;
- сомневаешься - оставь: прогон с ложным срабатыванием, выравнивающий хорошее предложение, хуже одного выжившего тега.

Самопроверка перед сдачей текста:

1. Есть попадания слова-тегов? Замени конкретикой или убери.
2. Три подряд предложения одной длины? Разбей одно.
3. Список добит до трёх? Верни истинное число.
4. Позиция спрятана за хеджированием? Назови её.
5. Абзацы заканчиваются формулами-переходами? Обрежь часть концовок резко.
6. Выдуманная конкретика? Убери или пометь как гипотезу.
7. Последний абзац пересказывает текст? Удали.
8. Текст звучит как голос обычного ассистента? Перепиши.

## Документация

Документы в `.docs/`:

- `AGENT_PROMPT.md` - главный промпт сессии, аудит, вопросы, контракт проверки, формат ответа.
- `DEVELOPMENT.md` - этот файл: постоянный контракт, зафиксированные решения, anti-slop.
- `TESTING.md` - контракт тестирования от поведения: матрица тестов, миграция существующих тестов, оси проверки.
- `SECURITY.md` - контракт безопасности: профиль, trust boundaries, capability budget, оси аудита, exfiltration proof.
- `DECISIONS.md` - журнал решений пользователя (чтобы не переспрашивать).
- `DESIGN.md` - дизайн-система: пресеты, токены, компоненты, правила UI/UX.
- `CHECKLIST.md` - чеклист перед/во время/после реализации.
- `REVIEWER.md` - промпт независимого ревью.
- `reviews/` - issue-файлы, создаются только когда независимое ревью находит проблемы.
- `agents-audit.prompt.md` - промпт аудита: сопоставление правил агентов с текущим кодом, поиск несостыковок/устаревшего/пробелов.

Когда новая информация появляется - помещай её в наименьший релевантный документ. Затем обнови индекс в этом файле, если добавлен новый тип документа.
